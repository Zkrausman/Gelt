# 🔒 ZAR-198 Atomic Shadow Journal Persistence

## 🎯 What

Shadow trade and cycle journals now mutate through a complete serialized transaction: read, validate JSON, mutate, write a private temporary file, sync and close it, then atomically replace the canonical journal. Trade and cycle append/update operations preserve malformed journals and surface errors rather than treating them as empty. `Save` also validates existing journal JSON before replacement. Engine-derived updates use strict one-to-one compare-before-write semantics, so a stale, missing, duplicate, or mismatched trade snapshot cannot overwrite a newer commit or claim a persisted exit.

Journal transactions use an OS file lock keyed by journal path, covering separate `Store` instances and supported Windows/Unix processes. `RunSession` logs structured errors and returns immediately on journal load, mutation, market-data failure for held positions, or cycle persistence failure. Entry and all exit claims—including alerts and verbose stdout for ordinary, pre-close, SELL, and end-of-day exits—occur only after the corresponding durable trade update succeeds. Cycle results are saved and published only after final pre-close/end-of-day mutations, and `TotalDeployed` is computed from persisted open positions. The daemon persists telemetry before its RUNNING status; either persistence failure cancels the daemon session, returns an error, and leaves the prior success status intact. STOPPED status reads the journal and reports persisted open deployment rather than fabricating zero.

## ⚠️ Risk

Previously, independently-created stores could overwrite each other's stale snapshots. Direct canonical writes could leave partial JSON after interruption, and malformed data could be overwritten. The engine also ignored persistence errors while claiming entries, exits, and successful cycles.

## 🛡️ Solution

- Path-scoped Windows `LockFileEx` and Unix `flock` locks serialize mutation transactions.
- Durable temp-file replacement preserves canonical journals, daemon telemetry, and daemon status on write/file-sync/replace failure and removes temporary artifacts. If the post-rename directory sync fails, the committed artifact remains successful and a structured `slog` warning records the reduced crash-durability assurance.
- Tests use isolated `t.TempDir()` journals and cover high-contention multi-instance and actual subprocess appends, strict stale/missing/duplicate/mismatched conditional-update rejection, corrupt-file preservation (including `Save`), injected replacement failure, and concurrent reads/writes.
- Engine persistence errors and held-position market-data failures fail closed before cycle callback/telemetry and before entry or exit claims, including verbose output. Focused tests inject a conditional conflict to prove no alert, callback, or verbose committed-exit claim occurs; successful pre-close handling proves exactly one post-commit alert and verbose claim.
- The daemon writes telemetry before RUNNING status through the same durable replacement path. Isolated injected telemetry/status/rollback failures prove pre-existing artifacts remain byte-for-byte intact for pre-commit failures; an unrecoverable rollback removes the new telemetry rather than leaving an unacknowledged fresh-success claim. STOPPED status derives deployed capital from the readable persisted journal.
- The daemon disables automatic orchestrator spawning by default. The existing heuristic bridge cannot automatically contaminate a promotable journal until it has a separately reviewed verified price/provenance contract.

## ✨ Result

The JSON journal cannot silently reset malformed data, lose same-path concurrent commits, or let a stale/missing/mismatched engine snapshot overwrite a newer record. Persistence failure stops the affected shadow session rather than emitting a live-equivalent success claim; callbacks/telemetry represent final persisted cycle state.

## Residual limitation

The inter-process lock is implemented for supported Windows and Unix local filesystems. Network filesystems with weak advisory-lock or rename guarantees are outside this contract. The existing orchestrator bridge remains unavailable for daemon auto-start because its hard-coded/random heuristic path lacks verified price/provenance. The compatibility setting cannot cause `RunBackground` to start it; any future bridge use requires a separate verified, non-promotable-contract decision.
