# Gelt Linear Ticket Implementation Specification: ZAR-100

## 1. Context & Multi-Hop Architectural Analysis

### State Lifecycle Trace
The `discord_bot_token` field is loaded at startup into the `AppConfig` struct from the local `~/.gelt/config.json`. When the daemon starts, it reads this token and creates a two-way persistent connection to the Discord Gateway via the `discordgo` package.

### Concurrency and Thread Safety
The bot's initialization and shutdown are synchronized with the daemon's lifecycle. `discordgo.Session` internally manages thread safety for reading and writing via the WebSocket connection. A `defer discordBot.Stop()` was added in `cmd/gelt/main.go` inside the daemon loop to ensure the session is closed without leaking resources or causing race conditions when the bot stops or the process terminates.

## 2. Metacognitive & Mathematical Deliverables

### Architectural Decision Record (ADR)
* **Design Choice**: Use `bwmarrin/discordgo` to maintain the persistent WebSocket connection instead of rolling a custom Gateway client.
* **Trade-offs**: Increases dependency footprint but significantly decreases implementation time and maintenance burden for managing Discord's internal Gateway reconnection and heartbeat logic.
* **Initialization Strategy**: Since this is a core listener, it gets instantiated directly within the daemon run loop of `cmd/gelt/main.go` inside an `if` block verifying the presence of a valid `DiscordBotToken`.

### Mathematical Constraints
Since this ticket primarily implements connectivity and structural scaffolding for Chat-Ops and does not interact with the Alpha Plan's asset models or pricing logic, mathematical constraints (e.g. Sharp ratio $SR = \frac{\mu - R_f}{\sigma}$) are not actively evaluated within this isolated module.
